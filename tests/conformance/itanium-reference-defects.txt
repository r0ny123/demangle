# Conformance corpus: names a reference demangler reads wrongly.
#
# Every other corpus here records what a reference demangler printed. These cannot, so
# the expected column is derived from the *declaration* instead. Thirteen of the entries
# have a source in tools/corpus_sources/reference_defects/: it is compiled with the
# compiler named on the entry, the symbol is read out of the object file with `nm`, and
# the spelling is what that source says the symbol's type is. Two more come from the
# general corpus sources named on them, and five are symbols out of shipped libraries,
# where the declaration is the library's own header or its published signature and the
# reading is spelled out in the entry's comment. That is the only ground truth a
# demangler has, and it is what settles a split between references.
#
# Almost all of these are one defect. A <template-param> is a substitution candidate in
# its own right (ABI 5.1.10), and the entry it contributes is *the parameter*, not the
# argument bound to it at the point the entry was made -- nor, for a component built
# over one, the composite that argument produced. The two differ whenever the
# back-reference is read under a different template scope, which is what happens in any
# name mentioning a local entity: the enclosing function's signature is written against
# that function's parameters, a `T_` inside it enters the table, and a later `S<n>_`
# naming that entry belongs to the *outer* template. The mangler does this because it
# canonicalises a template type parameter by level and index, so `T_` of one template
# and `T_` of another are one node to it.
#
# What each reference does, measured over the 217,730 distinct Itanium symbols in the
# shared libraries shipped on Ubuntu 24.04 (libLLVM 17/18/20, libclang-cpp, liblldb,
# libstdc++, libgphobos and the rest). Fixing this changed the output for 315 of them:
#
#   llvm-cxxfilt 18.1.3  differs from the corrected answer on 312 of the 315.
#   GNU c++filt 2.42     refuses 227 of the 315. Of the 88 it reads, it agrees with the
#                        corrected answer on 84. Of the 4 left, 3 are the
#                        `_Prepare_execution` constructor shape, where libstdc++'s own
#                        header settles it against both references; 1 is a generic
#                        lambda whose own parameter reaches it through a substitution,
#                        where GNU is right and this is not -- see ROADMAP.md heading 0.
#
