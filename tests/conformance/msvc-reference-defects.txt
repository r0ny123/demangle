# Conformance corpus: MSVC names `llvm-undname` reads wrongly, or not at all.
#
# Every other MSVC corpus here records what `llvm-undname` printed. These cannot, so the
# expected column is derived from the *declaration* instead -- and the declaration is not
# a guess: `tools/corpus_sources/msvc/msvc.cpp` is compiled with
# `clang++ --target=x86_64-pc-windows-msvc`, the symbol is read out of the object file
# with `nm`, and the spelling is what that source says the symbol's type is.
#
# The first three are one gap. `_L` and `_M` are `__int128` and `unsigned __int128` in
# the MS mangling, and `demanglePrimitiveType` in `MicrosoftDemangle.cpp` has neither --
# so LLVM's demangler refuses a name LLVM's own compiler emits. Checked against
# llvm-undname 18.1.3; `tools/generate_corpus.py` reads this file and excludes these, so
# a regeneration cannot record the refusal as the answer.
#
# `?bd@S@@QEBA_L_M@Z` is `__int128 S::bd(unsigned __int128) const`; the other two are the
# same pair as free-function parameters.
#
# The fourth is not a refusal but a wrong reading, which is the worse kind. A deduced
# return type is written `?` and a name -- `?A?<auto>@@` -- and a qualifier stands in
# front of it like any other type's, so `const auto structured_const()` is
# `?B?<auto>@@`. `CustomTypeNode::outputPre` in LLVM's `MSNodes.cpp` is
# `Identifier->output(OB, Flags);` and nothing else, where every other type node's
# `outputPre` writes its qualifiers first -- so `?A`, `?B`, `?C` and `?D` in front of a
# custom type all come back spelled the same, and the `const` is gone. Checked by
# compiling one rather than read off a table: `const auto structured_const()` in
# `tools/corpus_sources/msvc/modern.cpp`, next to the `auto structured()` whose
# unqualified `?A?<auto>@@` the reference does read.
#
# The last three are a refusal again. `?A_P` and `?A_T` where a return type goes are
# `auto` and `decltype(auto)`: what MSVC 14.3 writes for a function declared with one
# and not yet defined, so the compiler had nothing to write but the keyword, and `_P` and
# `_T` are types anywhere, so `$$QA_P` is `auto &&`. `demanglePrimitiveType` at 18 has
# neither; LLVM's main branch has both, and spells them so. The three are Boost 1.84's
# builds of the MSVC STL's `_Get_unwrapped`, `_Idl_distance` and `_Tuple_get`, declared
# `decltype(auto)`, `auto` and `auto&&` in <xutility> and <tuple>.
